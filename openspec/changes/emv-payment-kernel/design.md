## Module Boundary: Core vs. User-Implemented

| Layer | Owned by Kernel Framework | Owned by Integrator |
|-------|--------------------------|---------------------|
| HW Interface | Interface definition | IC Reader Provider |
| Platform Data | Interface + tag schema | param_read/write, iccdb_read/write impl |
| Crypto | Interface definition | crypto_driver_t implementation |
| UI | Interface definition (PIN prompt) | ui_driver_t implementation |
| Kernel Logic | Orchestrator skeleton + common helpers | per-kernel config, CVM plugin, risk plugin |
| Certificates | — | ACM(A) table registration |

## TLV Data Warehouse

Transaction-scoped, zero-copy, flat memory pool.

```c
typedef struct {
    uint32_t tag;       // EMV tag, 32-bit key
    uint8_t *value;     // pointer into shared pool (zero-copy)
    uint16_t len;       // value length
} tlv_entry_t;

#define MAX_TLV_ENTRIES   48

typedef struct {
    uint8_t  pool[MAX_POOL_SIZE];
    uint16_t pool_used;
    tlv_entry_t entries[MAX_TLV_ENTRIES];
    uint8_t count;
} tx_warehouse_t;
```

Key invariants:
- All `value` pointers point into `pool`; no heap allocation
- Each transaction gets a fresh warehouse (stack-allocated or caller-owned)
- Clear on transaction start: `pool_used = 0`, `count = 0`

Operations:
- `tlv_warehouse_init(wh, pool_size)` — reset for new transaction
- `tlv_store_set(wh, tag, src, len)` — alloc from pool + memcpy
- `tlv_store_get(wh, tag, dst, &len)` — lookup + copy out
- `tlv_validate_dict(dict, wh)` — check mandatory tags present
- `tlv_dump_raw(wh, buf, len)` — serialize all entries to raw TLV
- `tlv_dump_ordered(wh, tags, n, buf, len)` — serialize per tag order

## Kernel Data Dictionary

Replaces hard-coded branch logic. Each kernel has a dict that defines every tag it uses:

```c
typedef enum {
    TAG_SRC_TERMINAL,       // From POS params or terminal-known value
    TAG_SRC_CARD_GPO_RESP,  // Extracted from GPO response TLV
    TAG_SRC_CARD_OTHER,     // Read from card via other APDU
    TAG_SRC_GENERATED,      // Generated by terminal (TN, random)
    TAG_SRC_CONST,          // Fixed constant per spec
} tag_source_t;

typedef enum {
    TAG_TYPE_NUMERIC,     // BCD-encoded numeric (e.g., amount)
    TAG_TYPE_INTEGER,     // Raw integer (big-endian)
    TAG_TYPE_BINARY,      // Raw bytes, no interpretation
    TAG_TYPE_STRING,      // ASCII string
    TAG_TYPE_AID,         // AID / DF name (special binary + length rules)
    TAG_TYPE_BITMASK,     // Bit bitmap (AIP, AUC, TVR, TAR)
    TAG_TYPE_DATE,        // YYYYMMDD packed date
    TAG_TYPE_TIME,        // HHMMSS packed time
} tag_type_t;

typedef struct {
    uint32_t tag;
    tag_source_t source;
    tag_type_t type;
    uint8_t min_len;
    uint8_t max_len;
    uint8_t mandatory : 1;
    char description[40];
} dict_item_t;

typedef struct {
    uint8_t kernel_id;
    dict_item_t items[];           // Flexible array member
    uint8_t item_count;
    const cvm_plugin_t *cvm_plugin;
    const risk_plugin_t *risk_plugin;
} kernel_dict_t;
```

Framework uses the dictionary to:
1. Validate required inputs before kernel processing
2. Determine how to resolve each tag (query POS params, read from card, generate)
3. Build DOL bytes with correct encoding per tag type
4. Report errors when mandatory tags are missing

## Card Authentication (SDA/ODA)

Located in Entry Point Handler, after Application Select and before GPO.

### SDA Flow
1. Read ICA Public Key Certificate from card (`[9F21]`)
2. Verify certificate chain against ACM(A) using RSA-PKP
3. Extract DDIC (Decrypted Data Item for Ciphering)
4. Hash DOL data → compare with DDIC
5. On failure → decline transaction

### ODA Flow
1. Same cert verification as SDA
2. Execute Dynamic Number Layer: DES-decrypt ICData using ICA symmetric key
3. Send TOA with CDOL2 data
4. Verify ICC CRT (TDES-MAC of CDOL2 + ICDN) against `[9F7E]`
5. On failure → decline

Both require `crypto_driver_t` with `rsa_pkpad_verify` and `tdes_mac_verify`.

## Plugin Interfaces

### CVM Plugin
```c
typedef struct {
    cvm_result_t (*evaluate)(kernel_context_t *ctx);
    uint8_t (*get_method)(const kernel_context_t *ctx);
    uint8_t version;
} cvm_plugin_t;
```

Each kernel implements its own CVM strategy. K3 does Offline PIN, K5 does Crypto CVM (amount-only), K7 does token-specific checks.

### Risk Plugin
```c
typedef struct {
    risk_result_t (*check)(kernel_context_t *ctx, risk_check_type_t type);
    int (*build_tc_risk_data)(kernel_context_t *ctx, ttl_warehouse_t *tc_wh);
    int (*update_iccdb)(iccdb_t *iccdb, kernel_context_t *ctx);
    uint8_t version;
} risk_plugin_t;
```

Handles TRM, CRM, VEL, SDS per kernel requirements.

### Crypto Driver
```c
typedef struct {
    int (*rsa_pkpad_verify)(...);
    int (*des_decrypt)(...);
    int (*tdes_mac_verify)(...);
    int (*generate_cryptogram)(...);
    int (*ica_key_extract)(...);
} crypto_driver_t;
```

User implements per target platform (soft DES, HW AES-CMAC accelerator, etc.)

## Memory Model

```
Stack / static only. No malloc, no free.

Main workspace per transaction:
  tx_warehouse_t         (~3-5 KB depending on pool size)
  kernel_context_t       (~1-2 KB)
  outcome_result_t       (~256 bytes)

Total peak per transaction: ~7-10 KB RAM

Per-platform extras (caller-managed):
  crypto_driver_t state   (platform-dependent)
  iccdb persistent storage (external)
```
